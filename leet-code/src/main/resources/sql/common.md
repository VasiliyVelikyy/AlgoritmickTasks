# На LeetCode один и тот же запрос может давать разное время выполнения

## My solution

* Runtime 304 ms Beats 13.07%
* Memory 0.00 MB Beats 100.00%

```sql
SELECT p.firstName, p.lastName, a.city, a.state
FROM Person p
         LEFT JOIN Address a ON p.personId = a.personId
```

## Этот вариант работает быстрее

* Runtime 255 ms Beats 46.11%
* Memory 0.00 MB Beats 100.00%

```sql
select FirstName, LastName, City, State
from Person
         left join Address
                   on Person.PersonId = Address.PersonId
```

## А этот еще быстрее

* Runtime 240 ms Beats 84.80%
* Memory 0.00 MB Beats 100.00%

```sql
select Person.firstName, Person.lastName, Address.city, Address.state
FROM Person
         LEFT JOIN Address
                   ON Person.personId = Address.personId;
```


**Алиасы (псевдонимы) никак не влияют на время выполнения запроса.** Разница во времени на LeetCode (или
подобных платформах) — это «шум» самой тестирующей системы, а не особенность SQL.

Давайте разберем подробно, почему так происходит и как на самом деле работают алиасы.

### 1. Почему алиасы не влияют на скорость?

Когда вы отправляете SQL-запрос в базу данных (например, MySQL, PostgreSQL), он проходит несколько этапов:

1. **Парсинг (Parse):** База данных проверяет синтаксис и заменяет алиасы (`p` и `a`) на реальные имена таблиц (`Person`
   и `Address`).
2. **Оптимизация (Optimize):** Планировщик запросов строит план выполнения (Execution Plan).
3. **Выполнение (Execute):** База данных физически читает данные и соединяет их.

На этапе парсинга (шаг 1) алиасы «исчезают». Для базы данных оба ваших запроса выглядят **абсолютно идентично**.
Планировщик построит для них один и тот же план выполнения (скорее всего, один и тот же `Nested Loop Join` или
`Hash Join` с полным сканированием таблиц, так как там нет индексов и условий `WHERE`).

### 2. Почему тогда время на LeetCode отличается?

Платформы вроде LeetCode не являются идеальными бенчмарк-машинами. Разница между 304 мс и 240 мс вызвана внешними
факторами:

* **«Шумные соседи» (Noisy Neighbors):** LeetCode использует облачную инфраструктуру с общим доступом к ресурсам. В
  момент запуска вашего первого запроса на том же физическом сервере мог выполняться тяжелый запрос другого
  пользователя, который «съел» процессорное время или дисковый ввод-вывод (I/O).
* **Кэширование (Buffer Pool):** Если вы запускаете запрос несколько раз, при первом запуске данные могут считываться с
  диска (или из более медленного кэша), а при повторных — из оперативной памяти (RAM). Второй запрос (без алиасов) мог
  просто попасть в «теплый» кэш.
* **Сетевая задержка (Network Jitter):** LeetCode измеряет не только время работы СУБД, но и время передачи данных от
  контейнера с базой данных до контейнера с проверяющим скриптом. Сеть в микросервисной архитектуре может «лагать».
* **Холодный старт (Cold Start):** Контейнер с базой данных мог быть только что поднят (спящий режим), и инициализация
  заняла часть времени.

### 3. Почему Memory 0.00 MB?

LeetCode в SQL задачах не измеряет память, которую потребляет ваш запрос на стороне сервера (это технически сложно и
неинформативно для простых задач). Они измеряют только время. Значение `0.00 MB` — это просто заглушка платформы.

### Как правильно писать и относиться к этому на LeetCode?

1. **Всегда используйте алиасы.** Это лучший практик (Best Practice) в индустрии. Алиасы делают код короче, читабельнее
   и предотвращают ошибки, когда в разных таблицах есть колонки с одинаковыми именами (например, `id` или `created_at`).
2. **Не гоняйтесь за миллисекундами.** На LeetCode разница между 200 мс и 300 мс статистически незначима. Если ваш
   запрос логически верен и использует правильные JOIN'ы, а не декартовы произведения, вы молодец.
3. **Смотрите на перцентили, но с умом.** Если ваш запрос бьет 80%+ решений, значит, он оптимален. Если 13% — скорее
   всего, вы просто попали в момент высокой нагрузки на сервера LeetCode. Попробуйте отправить тот же самый запрос (с
   алиасами) еще 2-3 раза, и вы увидите, что время будет прыгать от 200 до 350 мс.

**Резюме:** Ваш первый запрос (с алиасами) написан более профессионально и правильно. Разница во времени — это просто
погрешность измерений платформы LeetCode.
